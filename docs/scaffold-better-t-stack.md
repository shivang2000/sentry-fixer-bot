## 1. Why this exists

We were about to hand-write package.json, tsconfig, eslint, vitest, docker-compose, drizzle, auth, tRPC, React, Vite, Tailwind, TanStack Router, Turborepo, and twenty other things. All of those choices align exactly with the defaults of `create-better-t-stack` (https://www.better-t-stack.dev/new). Adopting the scaffolder eliminates roughly three weeks of yak-shaving and locks us into a well-maintained, opinionated baseline. The domain code — webhook ingestion, dedup, triage, agent orchestration, PR open, MCP catalog, skill catalog, chat — is unchanged. The scaffold gives us a project skeleton we then layer business logic onto.

## 3. Auth model: Better-Auth as session/user store + WorkOS as identity provider

The user previously committed to WorkOS for its 1M MAU free tier and SSO-readiness. The scaffolder ships Better-Auth (self-hosted) by default. We use both:

- **Better-Auth** owns the `users` and `sessions` tables in our Postgres. Drizzle schema generated by the scaffold.
- **WorkOS AuthKit** is configured as a generic OIDC provider in Better-Auth's `providers` array. Users click "Sign in" → redirect to WorkOS-hosted login → callback → Better-Auth creates session.
- **Invites** are a custom table (not scaffold-provided). On callback, if no `users` row exists for the WorkOS-supplied email AND no `invites` row matches AND we're past the first-user-becomes-admin bootstrap, return 403.

The advantages over hand-rolled WorkOS:

- Free user/session schema + middleware + cookies from scaffolder
- Trivial to swap WorkOS for a second IdP later (Google OAuth, magic link, etc.) — Better-Auth supports them as additional providers
- DB-backed sessions → can revoke a session by deleting a row (WorkOS-only sessions are harder to invalidate)

The cost:

- One more library to learn (Better-Auth's configuration surface)
- The "first user becomes admin" bootstrap step needs custom code in Better-Auth's `events`/`callbacks`

## 6. What V2 frontend tasks change

V2 design (`v2-frontend-and-skills.md`) assumed we'd hand-build the frontend. Scaffolder gives us:

- React + Vite + Tailwind + TanStack Router pre-wired
- tRPC client wired
- Auth wired (Better-Auth + cookie sessions)
- Postgres + Drizzle schema for users/sessions

So V2 tasks 100-110 (frontend scaffold + WorkOS auth) shrink to:

- Configure Better-Auth's WorkOS OIDC provider (~half a day)
- Add `invites` table to Drizzle schema (~hour)
- Add first-user-becomes-admin bootstrap callback (~hour)
- Render login page using scaffolder's auth components (already exists for most providers; verify WorkOS provider renders a Sign in button or use generic OIDC button)

V2 tasks for repos/mcps/skills CRUD become "add tRPC routers + Drizzle migrations + UI pages" — unchanged in intent, easier in execution because the scaffolder gives the patterns.

V2 chat (PTY + WebSocket + OAuth URL capture) is unchanged. The scaffolder does not give us a PTY runner; we build that ourselves on top of `Bun.spawn({ stdio: ["pipe","pipe","pipe"], pty: true })`.

## 7. Risks introduced by the scaffolder choice

| Risk | Mitigation |
| --- | --- |
| **We don't control the scaffolder's choices** — if better-t-stack ships a breaking default change in a minor release, our scaffold output drifts | Pin the scaffolder version (`bun create better-t-stack@<exact-version>`) in `deploy/ec2/userdata.sh`-equivalent re-scaffold scripts; the version is recorded in `package.json` deps anyway |
| **Better-Auth + WorkOS OIDC may not be a first-class combination** in Better-Auth's docs; could need `genericOAuth` plugin | Spike during Task 0 to confirm; fall back to plain WorkOS Node SDK without Better-Auth if the integration is more pain than it's worth |
| **tRPC adds learning curve** for any contributor unfamiliar with it | Documented in README; the typed-end-to-end ergonomics are worth it |
| **Turborepo is overkill for a 2-app monorepo** in early days | Acceptable cost — `turbo run dev` and `turbo run test` are nicer than two terminal windows of `bun --watch`; cost is one config file |
| **`.claude/skills/` and `.mcp.json` from Skills/MCP addons are dev-side**, not runtime | We mirror the directory layout for our runtime feature: `/var/lib/sfb/skills/{id}/` + per-run-rendered `mcp_servers.json` lives in the run dir |
| **Biome's defaults differ from typical eslint/prettier** (e.g. no semis vs semis, single-quote vs double-quote) | Adopt scaffolder's defaults; consistency over preference; document the choice |
| **evlog wants Better-Auth context** — if we ever drop Better-Auth in favour of pure WorkOS, evlog needs adjustment | Acceptable since auth choice is part of this design lock-in |

## 8. Decision log additions (append to design.md)

| Decision | Rationale |
| --- | --- |
| Use create-better-t-stack to scaffold | Eliminates ~15 manual setup tasks; aligns with our exact stack choices |
| Better-Auth + WorkOS OIDC over WorkOS alone | Gets free user/session infra; preserves WorkOS as IdP per user pick |
| Drizzle ORM over raw `pg` | Type safety, migration tool, no extra cost since scaffolded |
| tRPC over REST | Type-safe end-to-end; sub-second feedback in the dev loop |
| Turborepo monorepo | Caches builds + tests; clean app boundaries between `server` and `web` |
| Biome over ESLint + Prettier | One tool, Rust-fast, single config |
| Husky for git hooks | Already widely-used; matches scaffolder default |
| evlog for request logging | Auth-aware + AI-SDK-aware logging matches our SRE-tool nature |
| Skills + MCP addons enabled | Free dev-side infra + reference patterns for our runtime feature |
| AI Example addon NOT enabled | We build our own chat; example is noise |

## 9. What the implementation order looks like (preview)

The detailed plan goes in `docs/plans/2026-05-15-scaffold-and-domain-plan.md` (next deliverable after design approval). High-level order:

```
A. Scaffold (~30 minutes)
   A1.  bun create better-t-stack@latest with all flags
   A2.  Verify scaffold builds + tests pass + dev server starts
   A3.  Commit "chore: scaffold via create-better-t-stack"

B. Configure WorkOS OIDC inside Better-Auth (~half day)
   B1.  Better-Auth config: add WorkOS OIDC provider via genericOAuth
   B2.  WorkOS-side OIDC client setup, redirect URI registration
   B3.  Add `invites` + bootstrap-admin callback
   B4.  Manual verify: GitHub login → user row → session cookie → /

C. Add Drizzle schema additions (~half day)
   C1.  alerts, runs, prs, budgets tables (copied from V1 plan §11)
   C2.  repos_config, mcp_installs, mcp_secrets, skill_installs, chat_*
   C3.  drizzle-kit generate + apply

D. Layer V1 domain code (Tasks 18-41 from previous plan, Drizzle-adapted)
   D1-D24.  Per V1 plan, swapping raw pg for Drizzle and execa for Bun.spawn

E. Layer V2 admin UI (repos / mcps / skills / runs / settings)
   E1-E18.  tRPC routers + Drizzle migrations + React pages

F. Chat (PTY + WebSocket + OAuth URL capture)
   F1-F8.   The interactive subprocess feature

G. Deploy (nginx, systemd, userdata, backup)
   G1-G5.   Same as V1 plan §43-44c with updated paths
```

Total: ~70 fine-grained tasks. Vs the previous 51 + 60 (V1 + V2) = ~111, that's a ~37% reduction. The eliminated tasks are scaffolding/glue; the kept tasks are domain logic.
